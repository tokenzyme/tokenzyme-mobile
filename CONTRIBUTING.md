# Contributing to Tokenzyme Mobile

Thanks for taking the time to contribute. This document covers how to get set up,
what we expect from a change, and how to get it merged.

By participating you agree to abide by the [Code of Conduct](./CODE_OF_CONDUCT.md).

## Before you start

Read the
[architecture guide](https://github.com/tokenzyme/tokenzyme-core/blob/main/ARCHITECTURE.md)
first if you have not. This client depends on two backend services, embeds a page from
the web client, and consumes ABIs copied by hand from the contracts repository — none
of which is obvious from the source alone.

Open an issue first for anything beyond a typo or an obvious bug fix.

Good first contributions:

- tests (there are none yet — see below);
- accessibility;
- replacing the chart WebView with a native chart, which would drop the dependency on
  `tokenzyme-app` being deployed;
- error handling and offline behaviour;
- documentation.

**Found a vulnerability?** Do not open an issue or a PR. Follow the private disclosure
process in [SECURITY.md](./SECURITY.md).

## Development setup

Requirements: Flutter with Dart SDK 3.6+, plus Xcode and/or the Android SDK.

You also need `tokenzyme-core` and `tokenzyme-indexer` running against a chain, and
`tokenzyme-app` served at `APP_URL` if you want charts. The architecture guide has the
[full sequence](https://github.com/tokenzyme/tokenzyme-core/blob/main/ARCHITECTURE.md#running-the-whole-stack-locally);
pointing everything at Sonic testnet is the quickest useful setup.

```bash
flutter pub get
cp .env.template .env   # then fill it in — every variable is documented inline
flutter run
```

On an emulator or simulator, `localhost` will not reach your machine. Use `10.0.2.2` on
the Android emulator, or your LAN IP.

```bash
flutter analyze   # static analysis
```

## Making a change

1. Fork the repository and branch off `main`.
2. Make your change. Keep it focused — one concern per pull request.
3. Run `flutter analyze` before pushing, and check it still builds.
4. Open a pull request describing what changed and why. Screenshots help for anything
   visual.

### Coding conventions

`analysis_options.yaml` is stricter than typical Dart style. Two rules in particular:

- **`always_specify_types` is on.** Write `String foo = ...`, never `var foo = ...`.
  This applies to generics too: `<Widget>[...]`, not `[...]`.
- **`prefer_single_quotes` is on.**

Beyond the linter:

- Screens are `HookConsumerWidget`. Shared async state goes in
  `lib/providers/providers.dart`; per-screen logic goes in a hook under `lib/hooks/`.
- Read configuration through `lib/utils/env.dart`, never `dotenv.env[...]` directly —
  that is where the required-variable checks live.
- Spacing and radii come from `lib/constants/`. Colours come from the theme, not from
  literals.
- Keep `lib/views/` organised by feature area, matching the existing layout.

### Working on signing flows

Anything that builds a transaction deserves extra care, because a bug there costs users
real money.

- What the user sees before signing must match exactly what gets signed — recipient,
  amount, token, contract address.
- Never derive a contract address, chain ID or RPC endpoint from remote data. Those
  come from `lib/utils/env.dart` and `lib/utils/reown.dart`.
- Preserve slippage bounds — the minimum-out passed on-chain must stay explicit.
- Token metadata is attacker-controlled. Validate the scheme on any token-supplied URL
  before opening it.

### Generated and copied code

Three things do not update themselves. Commit the regenerated output with the change
that caused it.

```bash
dart run build_runner build --delete-conflicting-outputs
```

- **`lib/graphql/*.graphql.dart`** — generated by `graphql_codegen` from the `.graphql`
  documents against `lib/graphql/schema.graphql`. Never hand-edit.
- **`lib/graphql/schema.graphql`** — a **manual copy** of core's schema. When core
  changes, refresh it from a running instance *before* regenerating, or codegen will
  cheerfully produce types for a schema that no longer exists.
- **`assets/launchpad_abi.json`, `assets/erc20_abi.json`** — **manual copies** of the
  ABIs from `tokenzyme-contracts`. After a contract change, copy the new ABI over the
  old one. Nothing detects the drift; `web3dart` just fails to find the function at
  runtime.

`.g.dart` files (Riverpod, json_serializable) come from the same `build_runner`
command.

### The chart comes from the web client

There is no native chart. `lib/views/token/tabs/info/chart.dart` loads
`<APP_URL>/tokens/<address>/chart` from
[`tokenzyme-app`](https://github.com/tokenzyme/tokenzyme-app) in a WebView. Chart bugs
are almost always fixed there, not here.

If you touch that WebView, read the
[WebView section of SECURITY.md](./SECURITY.md#the-chart-webview) first — it runs with
JavaScript unrestricted and deliberately has no channel back into Dart.

### On tests

This repository has no test suite. That is a gap, not a policy. A PR that establishes
one — even covering a single util — is very welcome, and worth opening an issue to
discuss the approach first.

## Dependencies

Dependabot opens **one grouped pull request per ecosystem, once a month**, containing
every minor and patch bump. Review it, check CI, merge.

**Major bumps are ignored by configuration and are the developer's job.** A major is a
migration: bumping the version in the manifest does none of the work, it just turns the
build red. When you want one, do it deliberately — read the upstream migration guide,
change the code it requires, and land it as its own reviewed pull request:

```bash
# edit pubspec.yaml, then:
flutter pub get
flutter analyze
```

Two things that still get through, on purpose or by accident:

- **Security updates ignore this policy**, which is intended. If a vulnerability's only
  fix is in a major, Dependabot proposes it regardless. Nothing merges itself — it
  arrives as a pull request, CI runs on it, and a human decides.
- **Packages below `1.0`.** Semver says any `0.x` bump may break, but Dependabot
  classifies `0.20 -> 0.21` as a minor, so it lands in the grouped PR. Give those
  entries a closer look than the rest.

## Review

A maintainer will review your PR. Expect closer scrutiny on anything touching a signing
flow. Please be patient, and be prepared to justify design decisions.
